# پروتکل مشترک و دروازه‌های ادامه/توقف

[فهرست](README.md) · [سه پایلوت](TOP_THREE.md) · [حدود تضمین](GUARANTEES_AND_Q1.md)

این برنامه مجوز اجرای API پولی، خرید GPU، دانلود حجیم، استفاده از دادهٔ خصوصی یا تغییر زمان‌بندی نیست. هیچ زمان تحویل آینده یا هزینهٔ cloud وعده داده نمی‌شود. تمام بودجه‌ها و thresholdهای عددی در اسناد، **پیشنهادِ پیش‌ثبت** هستند و قبل از test باید تصمیم نهایی دربارهٔ آن‌ها ثبت شود.

## G0 — دسترسی و قابلیت بازتولید

برای هر مدل دقیقاً checkpoint، commit/revision، tokenizer، license، نوع احتمال خروجی، امکان دریافت logit تمام گزینه‌ها و dependencyهای لازم ثبت شود. نام تجاری مدل جای این اطلاعات را نمی‌گیرد. API که تنها یک label می‌دهد برای همهٔ این آزمایش‌ها کافی نیست. وزن قابل دریافت هم به معنی مجوز آموزش/انتشار نامحدود یا pipeline آماده نیست.

برای داده، منبع اصلی، نسخه، شرایط استفاده، اجازهٔ انتشار مشتقات، unit of analysis، برچسب و نگاشت split ثبت شود. تا آن زمان وضعیت available-in-principle را با audited/usable جایگزین نکنید. ابتدا smoke test چند نمونه‌ای، memory profiling و کنترل خروجی؛ نه آزمایش بزرگ.

**No-go:** دسترسی قابل تکرار وجود ندارد، حقوق داده روشن نیست، یا probability کامل موردنیاز در دسترس نیست. fallback: backbone کوچک شفاف یا replay مجاز؛ دامنهٔ claim مطابق همین محدودیت کاهش یابد.

## G1 — پیشینه و سهم متمایز

برای کاندید منتخب دست‌کم نزدیک‌ترین مقالهٔ مستقیم، baseline ساده و کار معماری/روش مادر را کامل بخوانید. برای هرکدام یک جدول بنویسید: مسئله، فرض، اطلاعات قابل‌دسترس در train/test، الگوریتم، داده، بودجه و نتیجهٔ قابل‌مقایسه. به کد منبع هم فقط پس از review اعتماد شود.

یک جمله باید توضیح دهد: «اگر کار قبلی را دقیق بازتولید کنیم، کدام شکست باقی می‌ماند و چه آزمایشی نشان می‌دهد مداخلهٔ ما آن را رفع می‌کند؟» نام تکنیک تازه، زبان فارسی یا اضافه شدن یک head به‌تنهایی پاسخ نیست.

**No-go:** تمایز فقط اسم‌گذاری، یک ترکیب قبلاً انجام‌شده یا افزایش ظرفیت/داده است. خروجی محدود به replication یا نقد روش باشد؛ این هم تعهد چاپ نمی‌آورد.

## G2 — پایلوت و انتخاب معیار

اول یک backbone و یک مداخله. از سه seed برای غربال اولیه استفاده شود؛ تعداد seedِ لازمِ مطالعهٔ اصلی با واریانس پایلوت و محدودیت compute تعیین شود. پنج seed برای مطالعهٔ اصلی یک پیشنهاد عملی است، نه قانون ژورنال. seedهای generator، انتخاب pool و آموزش جدا ثبت شوند.

پس از مشاهدهٔ pilot روی train/dev، primary metric، minimal effect، guardrail، خانواده‌های test، baseline اصلی، بودجهٔ tuning و روش inference آماری freeze شوند. معیار موفقیت را بعد از دیدن test عوض نکنید. metric ثانویه‌ای که بهتر شده جایگزین primary ناموفق نشود مگر با برچسب exploratory و مطالعهٔ تأییدی جدید.

**Go:** شکست baseline در بیش از یک خانواده مشاهده شود، مداخلهٔ کوچک از explanation سادهٔ ظرفیت/داده عبور کند، و تخمین هزینه برای مطالعهٔ مستقل قابل‌قبول باشد. اعداد نمونهٔ TOP_THREE فقط starting contract هستند.

## جداسازی داده و جلوگیری از نشت

نمونهٔ مادر، paraphraseها، ترتیب‌های مختلف، aliasها و ترجمه‌های یک سؤال همگی یک group_id دارند. split قبل از تولید variant صورت گیرد. train برای وزن‌ها، dev برای انتخاب معماری/روش، calibration برای اصلاح confidence یا certification، و test برای گزارش نهایی است. اگر calibration برای انتخاب کالیبراتور هم مصرف شود، inner split لازم است. schema family و مجموعهٔ برچسب‌ها به‌صورت holdoutهای جدا بررسی شوند؛ فقط تصادفی کردن سطرها کافی نیست.

permutationهای یک پرسش n مستقل تولید نمی‌کنند. برای آزمون‌های binomial رسمی یک نمایش ازپیش‌تعیین‌شده از هر نمونهٔ مستقل استفاده شود، یا قضیه‌ای مناسب ساختار cluster ارائه گردد. bootstrap تجربی گروهی جای فرض iid یک قضیه را نمی‌گیرد. test دوزبانه باید در سطح جفت split شود. corpus بازیابی، answer key و trajectory oracle نباید اطلاعات test را وارد آموزش کنند.

## baseline و کنترل منصفانه

مدل خطی/طبقه‌بند ساده، head-only، baseline منتشرشدهٔ نزدیک و در صورت ارتباط یک مدل مولد در کنار decision scorer باشند. preprocessing، تعداد برچسب، allowed context و budget tuning برابر و تفاوت‌های اجتناب‌ناپذیر گزارش شوند. پارامتر کل، پارامتر trainable و active FLOPs اعداد متفاوت‌اند؛ هر سه در MoE ثبت شوند.

LoRA در کنار تغییر head، calibration، quantization و augmentation باید ablation مستقل داشته باشد. برای distillation تعداد query معلم و برای search تعداد query oracle کنترل شود. یک solver/مدل بزرگ «حقیقت» نیست مگر قرارداد مسئله آن را با شاهد معتبر oracle بداند.

## آمار و هزینه

برای test معمول، paired bootstrap در سطح group_id با بازهٔ اطمینان 95٪ و گزارش per-family پیشنهاد می‌شود. چند seed به‌تنهایی استقلال چند dataset را نمی‌سازند. برای چند مقایسهٔ تأییدی، خانوادهٔ آزمون‌ها از قبل مشخص و اصلاحی مانند Holm یا روش معتبر متناسب استفاده شود؛ بقیه exploratory برچسب بخورند. آزمون آماری جای حد اثر عملی را نمی‌گیرد.

برای گواهی ریسک، قرارداد دقیق و تصحیح انتخاب policy در GUARANTEES_AND_Q1 لازم است. confidence interval مربوط به امتیاز رتبه‌بندی ساخته نشود؛ آن امتیاز یک قضاوت است نه نمونه‌گیری آماری.

زمان‌سنجی شامل hardware، نرم‌افزار، precision، batch، concurrency، warm-up، طول ورودی/خروجی و caching است. latency end-to-end و p50/p95 را جدا از throughput گزارش کنید. عدد speedup upstream به عنوان نتیجهٔ ما وارد جدول نشود. صرف sparse بودن وزن یا کم شدن FLOPs، سرعت kernel واقعی را اثبات نمی‌کند.

## G3 — مطالعهٔ تأییدی

پس از عبور از پایلوت، مدل دوم یا خانوادهٔ دادهٔ بیرونی اضافه شود. نمونهٔ ادعای محدود قابل آزمون: «در قرارداد مشخص و مجموعهٔ ارزیابی ثبت‌شده، روش از baseline X بهتر است»، نه «برای همهٔ تصمیم‌ها بهتر است». نتایج منفی، کم‌نمونه بودن گروه‌ها و failure cases منتشرشدنی حفظ شوند.

**No-go:** effect در دادهٔ بیرونی ناپدید شود، با baseline قوی‌تر توضیح داده شود، یا هزینهٔ کامل از بودجه خارج شود. rerun با همان test برای پیدا کردن winner، test جدید مستقل نیست.

## G4 — آماده‌سازی ادعای مقاله و ژورنال

خروجی لازمِ پیشنهادی: صورت مسئلهٔ دقیق، جدول پیشینهٔ نزدیک، ادعای محدود با شواهد، ablation، limitation، کد و config قابل‌تکرار، manifest داده و مدل و مسیر انتشار مجاز. بازتولید یک نتیجهٔ اصلی از محیط پاک انجام شود. برای هر claim یک run_id یا proof/reference مشخص شود.

رکورد Q1 مطابق GUARANTEES_AND_Q1 تکمیل شود. یک مقالهٔ با کیفیت و مناسب scope هنوز ممکن است پذیرفته نشود؛ رتبهٔ ژورنال جانشین تصمیم علمی داور نیست. در حال حاضر **همهٔ کاندیدها پیش از G0/G1 کامل** هستند و هیچ G2/G3 واقعی در این تغییر اجرا نشده است.
