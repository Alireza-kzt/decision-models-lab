# پروتکل تبدیل روش موجود به آزمایش قابل دفاع

[بانک](README.md) · [قالب مدخل](METHOD_TEMPLATE.md). این سند برنامهٔ آزمایش است، نه قابلیت پیاده‌سازی‌شدهٔ کامل در runner فعلی.

## ۱. ابتدا قرارداد مسئله

واحد نمونه را تعریف کنید: state، schema، پرسش، گزینه‌های معتبر و target. مشخص کنید خروجی تک‌برچسبی، چندبرچسبی، ترتیبی، پیوسته یا تصمیم مشترک چندفیلدی است. ارزیابی زیر هر قرارداد متفاوت است. «typed» یا JSON صحیح به معنی درست بودن معنایی نیست.

دسترسی واقعی checkpoint/API را ثبت کنید: weights، gradients، hidden features، logits کامل، sampling و کنترل decoding. روش‌های W/F/A را صرفاً با نام تجاری مدل سازگار فرض نکنید.

## ۲. Baseline قبل از ترکیب

برای مسئلهٔ مناسب، majority/uniform، classifier سادهٔ آموزش‌دیده، head-only، full FT و LoRA را بررسی کنید. همهٔ آن‌ها برای همهٔ قراردادها مناسب نیستند؛ دلیل انتخاب یا حذف ثبت شود. برای MoE علاوه بر پارامتر کل، compute فعال و latency را کنترل کنید. برای DFlash، decoding عادی و drafter مناسب روی یک هدف ثابت لازم است؛ classifier غیرمولد baseline جداگانه است.

اثر هر جزء به‌تنهایی مشخص شود؛ سپس طراحی ۲×۲ یا ablation برای تعامل اجزا. «روش الف+ب+ج» بدون کنترل، علت بهبود را نشان نمی‌دهد.

## ۳. جداسازی داده

train برای fit، dev برای انتخاب روش و hyperparameter، calibration برای threshold/temperature/sets و test قفل‌شده برای نتیجهٔ نهایی. split بر اساس منبع، template، مسئلهٔ پایه، گراف یا خانوادهٔ schema باشد؛ paraphraseها و ترجمه‌های یک نمونه در یک گروه بمانند.

retrieval index، synthetic generation، teacher labeling، active learning، quantization calibration و meta-learning هم باید این جداسازی را رعایت کنند. هرگونه online/test-time adaptation به‌عنوان پروتکل جدا ثبت شود.

## ۴. معیارها

| بعد | معیار پیشنهادی | نکته |
|---|---|---|
| صحت | Accuracy، Macro-F1، معیار مناسب رتبه/رگرسیون | نامناسب بودن metric برای قرارداد را بررسی کنید |
| احتمال | NLL، Brier، reliability diagram و ECE با bins مشخص | ECE تنها معیار تصمیم‌گیری نباشد |
| امتناع | risk–coverage، خطای پذیرفته‌شده، پوشش گروهی | همهٔ روش‌ها در پوشش قابل مقایسه |
| مجموعهٔ پاسخ | coverage و اندازهٔ مجموعه | فرض‌های conformal و دامنهٔ ضمانت صریح |
| چندفیلدی | exact match مشترک، نقض قید و صحت معنایی | اعتبار نحوی و معنایی جدا |
| پایداری | permutation، تغییر تعداد گزینه، distractor، paraphrase | تبدیل باید target را درست حفظ/تبدیل کند |
| هزینه | p50/p95، throughput، peak VRAM، هزینهٔ کل | warm/cold، batch، سخت‌افزار و precision ثابت |
| یادگیری | تعداد label، زمان انسان، compute آموزش | هزینهٔ انتخاب داده و teacher نیز محاسبه شود |

runner موجود همهٔ این metricها و آزمایش‌ها را پیاده‌سازی نمی‌کند. افزودن هرکدام وظیفهٔ کدنویسی و تست جداست. metricهای اضافی این سند «نتیجهٔ موجود» نیستند.

## ۵. عدم‌قطعیت آماری و انتخاب آزمایش

برای مدل‌های stochastic چند seed و dispersion گزارش کنید. برای مقایسهٔ پیش‌بینی‌ها، bootstrap یا آزمون زوجی متناسب با طراحی به‌کار رود؛ اگر نمونه‌ها گروه‌بندی شده‌اند، گروه واحد resampling باشد. تعداد seed/sample را با بودجه و توان کشف اثر انتخاب کنید، نه عدد نمایشی ثابت.

از قبل primary metric، حداقل اثر عملی مهم و guardrailهای کیفیت/هزینه مشخص شوند. 108 روش به معنی 108 فرصت جست‌وجوی آزاد روی test نیست. sweepها، انتخاب‌های منفی و multiple comparisons ثبت شوند. روش برنده را پس از انتخاب روی holdout استفاده‌نشده ارزیابی کنید.

## ۶. بازتولید و حقوق استفاده

model ID، revision، tokenizer، dataset hash، کد و dependency lock، precision، GPU/CPU، seed، prompt/schema و decoding settings در manifest اجرای واقعی ذخیره شوند. model weights و داده‌های دارای محدودیت در Git قرار نگیرند. قوانین مجوز و شرایط API قبل از استفاده بررسی شوند.

## ۷. چه چیزی مقاله نمی‌شود؟

صرف افزودن LoRA، تعویض loss، اجرای MoE، استفاده از RAG یا افزایش تعداد expertها ادعای تازگی نیست. مسیر قابل دفاع چنین است: شکست مشاهده‌شده → مرور نزدیک‌ترین پیشینه → فرضیهٔ دقیق → روش یا تحلیل متمایز → baseline منصفانه → شواهد بازتولیدپذیر و محدودیت‌ها.

نتیجهٔ منفی معتبر است: بهبود نداشتن calibration بعد از quantization، نبود speedup روی خروجی کوتاه یا شکست router در schema ندیده، همگی می‌توانند دانستهٔ مفید باشند؛ ارزش انتشارشان باید پس از مشاهدهٔ شواهد ارزیابی شود.
