# بازتولیدپذیری و ثبت آزمایش

## یک run چگونه قابل دفاع می‌شود؟
هر run باید به experiment ID و commit وصل شود و command، config، seed، نسخهٔ Python و dependencies، مدل/revision، tokenizer، hardware، dataset hash، split hash، raw prediction hash، وضعیت خطا و معیارهای محاسبه‌شده داشته باشد. فایل result را دستی اصلاح نکنید؛ محاسبه را دوباره با run جدید انجام دهید.

## runner فعلی
ورودی‌ها کپی نمی‌شوند؛ hash آن‌ها و probabilities اعتبارسنجی‌شده ثبت می‌شوند. خروجی run ابتدا running و بعد completed/failed می‌شود. خطا در فایل failure ثبت می‌شود و پوشه حفظ می‌گردد. وقتی Git موجود نباشد revision کد null ثبت می‌شود؛ این اجرای پژوهشی قابل استناد نهایی نیست.

## سه سطح تکرار
تکرار command با همان ورودی، تکرار seedهای آموزش، و بازتولید با محیط مستقل سه چیز متفاوت‌اند. خروجی hosted ممکن است با نسخهٔ پشت سرویس تغییر کند؛ timestamp و model version برگشتی را ذخیره کنید. صرف یک seed ثابت تضمین bitwise determinism نیست.

## ثبت تصمیم
برای تغییر مهم ADR بنویسید: مسئله، گزینه‌ها، انتخاب، پیامد، شرط بازنگری و مدرک. آزمایش‌های ناموفق حذف نشوند. گزارش باید نشان دهد چند config امتحان شده‌اند، نه فقط بهترین run.

## بازتولید قبل از مقاله
از checkout تازه شروع کنید؛ dependencies و داده را از revision ثبت‌شده بازیابی کنید؛ testها را اجرا کنید؛ جدول و شکل را از raw evidence بسازید؛ تمام خانه‌های جدول را به run و همهٔ claimها را به همان جدول وصل کنید. حداقل یک اجرای مستقل از محیط اصلی انجام دهید.
